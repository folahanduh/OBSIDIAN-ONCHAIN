# Tenebra L1: sovereign chain and native coin

Status: **runs on CometBFT.** The economic core (`crates/tenebra-chain`) and
the node (`crates/tenebra-node`) produce blocks with real BFT consensus on a
local devnet (tested with 4 validators). No DEX module yet, no public network.

## 0. Run it

You need Rust, Go ≥ 1.22 and Python 3 (for the setup script).

```bash
# once: install CometBFT
go install github.com/cometbft/cometbft/cmd/cometbft@v0.38.26
export PATH=$PATH:$(go env GOPATH)/bin

# start a devnet (1 validator; or `scripts/devnet.sh 4` for four)
scripts/devnet.sh
```

Then, in a second terminal:

```bash
T=target/release/tenebra-node
K=~/.tenebra-devnet/keys
$T query summary                                   # height, supply, burned fees, validators
$T keygen --out $K/bob.json                        # prints bob's address
$T tx transfer --key $K/alice.json --to <bob address> --amount 25
$T query balance/<bob address>
$T tx delegate --key $K/bob.json --validator $($T address --key $K/validator0.json) --amount 10
$T query delegation/<bob address>/<validator address>
```

`alice` is funded with 1,000,000 coins at genesis. Each validator has a
10,000-coin self-bond.

- **Stopping and restarting.** `Ctrl-C` stops everything; rerunning
  `scripts/devnet.sh` restarts it. The app keeps state in memory, so on restart
  CometBFT replays all blocks into it. That's deterministic, and CometBFT
  verifies the state hashes as it goes. Use `--reset` for a fresh chain.
- **Running it by hand** instead of through the script:

  ```bash
  cometbft init --home ~/.cmt
  tenebra-node init-devnet --home ~/.cmt
  tenebra-node start &
  cometbft start --home ~/.cmt --proxy_app tcp://127.0.0.1:26658
  ```

Verified here: blocks produced with 1 and 4 validators, all 4 nodes agreeing
on every block's state hash. A transfer sent through one node was visible on
another. With one of 4 validators killed, the chain kept going (3/4 > 2/3).
After a full restart, 33 blocks replayed into identical state. CI repeats the
4-validator test on every push (`scripts/devnet-smoke.sh 4`).

## 1. Architecture

```
          ┌──────────────── validator node ────────────────┐
 txs ───► │  CometBFT (Go)                                  │
          │   p2p · mempool · block proposal · BFT voting  │
          │   finality · double-sign evidence              │
          │            │  ABCI 2.0 (local socket)           │
          │            ▼                                    │
          │  Tenebra app (Rust)                             │
          │   tenebra-chain   coin ledger · gas burn ·      │
          │                   staking · slashing            │
          │   tenebra-engine  dark-pool order book (next)   │
          │   tenebra-privacy sealed txs · viewing keys     │
          │   tenebra-auth    session keys for HFT          │
          └────────────────────────────────────────────────┘
```

**Why CometBFT + a Rust application.** Consensus is the part of a blockchain
that is hardest to get right, and the costliest when it's wrong. CometBFT is
battle-tested BFT consensus (it secures the Cosmos ecosystem, dYdX v4,
Celestia). It drives any application through the ABCI interface, so our Rust
engine stays as is. This is exactly how **Penumbra** (a private DEX L1) and
**Namada** (a privacy L1) are built.

The alternatives:
- **Fork Solana's validator:** you would maintain millions of lines you didn't write.
- **Cosmos SDK:** it's Go, so the matching engine would be rewritten.
- **From scratch:** years of consensus research.

`tenebra-chain` is a pure, deterministic state machine. Same blocks in → same
state and app hash out on every validator (tested by replaying random block
histories on two nodes).

## 2. The native coin ($TENEBERA) — what it does on-chain today

| Role | Mechanism | Code |
|---|---|---|
| **Gas** | Every transaction pays `gas × base_fee` in the native coin. **The fee is burned.** | `deliver_tx` |
| **Fee market** | EIP-1559 base fee: +12.5% per full block, −12.5% per empty block, floor at `min_base_fee`. No tips, so there is no auction for ordering | `update_base_fee` |
| **Security** | Validators bond the coin; the top `max_validators` by stake form the consensus set (sent to CometBFT as power updates) | `update_validator_set` |
| **Delegation** | Holders delegate to validators via shares; rewards and slashes apply pro-rata automatically | `delegate` / `undelegate` |
| **Issuance** | New coins go only to validators that **signed** the previous block, by voting power. Commission goes to the operator, the rest to delegators. Rate decays linearly (default 8% → 1.5%) | `mint_issuance` |
| **Slashing** | Double-signing: 5% burned, plus unbondings started after the offence, then permanent ban ("tombstone"). Downtime: 0.01% burned, then jail; `Unjail` after the jail period | `punish_double_sign`, `track_downtime` |
| **Unbonding** | 21 days (default), still slashable during that time | `end_block` |

Supply moves in exactly four ways: genesis, issuance (+), fee burn (−) and
slashing (−). After every block, tests check that
`supply = balances + bonded + unbonding + unclaimed rewards`. The reward
escrow can never owe more than it holds, and both properties are checked
across thousands of random blocks. Planting a bug in either the slashing or
the minting accounting makes those tests fail.

Value accrual follows from this: usage burns coins and validators earn
issuance. Once the DEX module lands, stakers also earn a share of trading fees
in USDC. The protocol can then buy back and burn the native coin on its own
DEX, with no external router or bridge involved.

## 3. Notes on the blueprint

| Blueprint idea | Assessment | What we do instead / additionally |
|---|---|---|
| Slash validators who reorder trades | Only **provable** offences can be slashed, and ordering preferences aren't provable in general | (1) Encrypted transactions: the proposer orders ciphertexts it can't read, and the order is committed before decryption (`OrderingLog`, built), so reordering after the commitment is provable and slashable. (2) Per-block **batch auctions** at one uniform price, so order within a block is worth nothing and there's nothing to front-run. Penumbra and CoW Protocol use the same idea |
| Guard "compiled into consensus" | Yes, this is natural on our own chain | Limit prices, slippage bounds and fees become protocol rules of the DEX module (`tenebra-engine` already enforces mandatory limits and bounded matching) |
| 1,000-sub-wallet shuffler for privacy | Weak: moving funds between your own addresses is easy to link by amount and timing, and it breaks compliance linkage | Encrypted balances/fills plus per-epoch viewing keys (`tenebra-privacy`, built). Balances are hidden from the public, and a CEX can audit when the user grants access. Can still be marketed as "Shield" |
| Trades in < 50 ms | Matching: yes (measured ~0.2 µs median). Final settlement across a global validator set: no. BFT needs several network round trips, so ~0.5–1 s is realistic | Fast matching; target ~1 s finality |
| "Quantum consensus" | Not a buildable feature today | Post-quantum signatures are a separate, long-term migration item |

## 4. Decisions needed from you

1. **Spelling and ticker.** Earlier we chose *Tenebra*; your latest plan says
   *TENEBERA*. It's a single genesis setting (`native_symbol`), but brand,
   domain and ticker should match before launch.
2. **Supply and allocation.** Total supply, splits (community / team /
   investors / validators / treasury), vesting schedules. Placeholder
   parameters only so far.
3. **Issuance curve.** Default 8% decaying 1%/year to a 1.5% floor
   (Solana-like). Higher attracts validators early but dilutes holders.
4. **Validator set size** (default 3 in tests; production 50–150) and
   **minimum self-bond**.

## 5. Roadmap (L1)

1. ~~ABCI connection + local devnet~~ (done). Next for the node: on-disk
   state with snapshots, so restarts don't replay from genesis.
2. **DEX module.** Markets on `tenebra-engine`, balance locking, trading fees →
   USDC real yield to stakers, protocol buyback-and-burn with a TWAP bound
   (`tenebra-quant`).
3. **Sealed transactions → threshold decryption** (validators' decryption
   shares carried in CometBFT vote extensions) **→ batch auctions.**
4. **Session keys** (`tenebra-auth`) for high-frequency trading, and **encrypted
   fills + viewing keys** (`tenebra-privacy`).
5. **USDC bridge** in from Ethereum/Solana. This is the riskiest component in
   most chains' history, so it needs a careful design and audit.
6. **Merkle state tree** for light clients (replacing the flat app hash),
   governance, block explorer, RPC/SDKs, wallets.
7. Public testnet, external security audits, then mainnet.

The Solana router (`solana/`, `docs/TOKENOMICS.md`) is **parked**. Its maths
(`tenebra-tokenomics`: discount curve, staking rules, reward pools) carries
over to the L1's DEX fee and staking design.
